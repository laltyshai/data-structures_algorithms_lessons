## Важно для P4 (как пользоваться `registry.parquet`)

- **Не суммировать таблицу целиком.** В ней с флагами лежат:
  - лишние копии дублей: `is_dup_extra == True` (60 строк: 53 продажи + 4 возврата + 3 войда);
  - корпоративные: `party_type == "corporate"` (не субагенты, исключить);
  - нерешённые контрагенты: `party_type == "unresolved"`.
- `amount_kgs` — на один билет, знак по логике ETM; `amount_row_kgs` — на всю строку.
- `ticket_in_amount` (65 строк): `amount_kgs` пусто, реальную сумму брать из ETM.
- `subagent_id` — строка в формате P2 (`тянь-шаньтур`), её можно напрямую сопоставлять с `subagent_key` в `acts_clean.csv` и `agent_key` в `etm_clean.csv`.

## Выводы для P5

- **Войды.** В реестре войд = тариф продажи **без сервисного сбора**, пересчитанный по курсу дня войда (исходная сумма совпадает с продажей 751 из 751).
  Бот в ETM возвращает полную сумму продажи со сбором по курсу продажи (674 из 676).
  Разница по войдам = сбор + курсовая разница.
- **Продажи бота, сумма не совпала** (по билетам ETM): KGS с разницей ≥2% — 78; валюта <2% — 417 (похоже на другой курс у бота); валюта ≥2% — 168; номер билета вместо суммы — 113 билетов ETM.
- **Дубли**: кроме 53 продаж, есть полные дубли 4 возвратов и 3 войдов.
- **Пассажиры**: в 70 строках число пассажиров ≠ числу билетов; порядок пассажиров не совпадает с ETM (совпадение 69%), поэтому `passenger` — вся строка пассажиров, а не один человек на билет.
- Обрезанные имена (19 ключей) — тоже ошибка агента в реестре (`party_match = prefix`).
